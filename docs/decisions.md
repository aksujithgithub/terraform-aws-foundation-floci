# Architecture Decision Records

## ADR-001: Use floci for local AWS emulation

**Status:** Accepted

**Context:** We need to develop and test Terraform against AWS services without incurring costs or requiring a real AWS account for every engineer.

**Decision:** Use [floci](https://floci.io) (built on LocalStack) as the local AWS emulator. `floci start` + `eval "$(floci env)"` injects environment variables so the AWS CLI and Terraform provider automatically target `http://localhost:4566`.

**Consequences:** Local state is ephemeral — it resets on `floci stop`. The provider block is generated by Terragrunt's root `generate` block and auto-targets LocalStack.

## ADR-002: Use Terragrunt for environment orchestration

**Status:** Accepted

**Context:** Plain Terraform root configs duplicate provider, backend, and version blocks across environments. As environments grow (local → staging → prod) this becomes error-prone.

**Decision:** Use [Terragrunt](https://terragrunt.gruntwork.io) to DRY up the configuration. A root `terragrunt.hcl` generates the provider and versions blocks, configures the backend, and exposes common inputs. Each environment is a folder (`environments/local`) containing per-stack `terragrunt.hcl` files that call `terraform { source = "..." }`.

**Consequences:** 
- Adding a new environment is a new folder with overridden inputs only.
- `dependency` blocks replace manual output wiring between stacks.
- Modules remain pure Terraform — no Terragrunt awareness inside `modules/`.

## ADR-003: Use local backend for the local environment

**Status:** Accepted

**Context:** LocalStack does not reliably replicate S3-based Terraform remote state.

**Decision:** The root `terragrunt.hcl` configures a `local` backend for the local environment, storing state under `.terragrunt-state/`. Real environments will override this with an S3 + DynamoDB backend.

**Consequences:** State is not shared, which is acceptable for single-developer local environments. `.terragrunt-state/` is gitignored.

## ADR-004: Module-per-concern structure

**Status:** Accepted

**Context:** A monolithic Terraform configuration becomes hard to maintain as infrastructure grows.

**Decision:** Split infrastructure into reusable modules (`network`, `iam`). Each Terragrunt stack maps 1:1 to a module. Stacks declare explicit `dependency` blocks to share outputs across modules.

**Consequences:** Slight increase in file count, but strong separation of concerns, independent apply/destroy per stack, and reusability across environments.
